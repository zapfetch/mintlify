If you're already running against Firecrawl Cloud (`api.firecrawl.dev`),
ZapFetch is a drop-in replacement: change one base URL, swap the API key,
ship. No code refactor, no new SDK to learn, no schema migration.
ZapFetch is wire-compatible with both the `/v1/*` and `/v2/*` Firecrawl
endpoints.

## ZapFetch vs Firecrawl Cloud at a glance

| | Firecrawl Cloud | ZapFetch |
| --- | --- | --- |
| API surface | `/v1`, `/v2` | `/v1`, `/v2` (wire-compatible) |
| SDKs | `firecrawl-py`, `@mendable/firecrawl-js` | **Same SDKs** — only `api_url` changes |
| Billing | USD, monthly minimums | USD, no minimums, no commits |
| Edge region | US-east default | **Singapore-hosted, APAC-native** |
| Format multipliers | Markdown + HTML + screenshot = multiple charges | All formats included in **1 credit** |
| Failed requests | Charged | **Free** — 4xx, 5xx, timeouts, robots.txt denials |
| Crawl billing | Per page dispatched | Per page **successfully fetched** |
| Lock-in | Vendor SDK only | Standard `firecrawl-*` SDKs — no lock-in |

The migration is three changes — base URL, key, optional client config — and
takes under ten minutes for most apps.

## Why migrate?

- **USD billing, metered by usage.** No commits, no minimums, no surprise
  overages; every response tells you how many credits remain.
- **Same SDKs, same schemas.** You keep using `firecrawl-py` and
  `@mendable/firecrawl-js`. No vendor-specific client, no lock-in.
- **Both v1 and v2 endpoints supported.** Whichever version your current
  Firecrawl SDK talks, ZapFetch accepts it — no pinning required.
- **APAC-native edge.** Singapore-hosted API means lower latency for
  scraping `.jp`, `.kr`, `.cn`, `.tw`, `.sg` targets, and fewer
  geo-blocks on regional sites.

## Step 1 — Get a ZapFetch API key

1. Sign in to the [ZapFetch Console](https://console.zapfetch.com/dashboard) with GitHub, Google, or
   email.
2. Open **Dashboard → API keys**.
3. Click **Create key**. Copy the UUID API key — it's shown once.

ZapFetch API keys are UUID strings, not `fc-` prefixed Firecrawl Cloud keys.
If your existing config validates the `fc-` prefix, relax that validation
before switching traffic.

## Step 2 — Swap the base URL

Point your SDK or HTTP client at `https://api.zapfetch.com`.

### curl

```diff
- curl -X POST https://api.firecrawl.dev/v1/scrape \
+ curl -X POST https://api.zapfetch.com/v1/scrape \
    -H "Authorization: Bearer YOUR_ZAPFETCH_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{ "url": "https://example.com", "formats": ["markdown"] }'
```

### Python

```diff
  from firecrawl import FirecrawlApp

- app = FirecrawlApp(api_key="YOUR_ZAPFETCH_API_KEY")
+ app = FirecrawlApp(
+     api_key="YOUR_ZAPFETCH_API_KEY",
+     api_url="https://api.zapfetch.com",
+ )
```

### Node.js

```diff
  import FirecrawlApp from "@mendable/firecrawl-js";

- const app = new FirecrawlApp({ apiKey: "YOUR_ZAPFETCH_API_KEY" });
+ const app = new FirecrawlApp({
+   apiKey: "YOUR_ZAPFETCH_API_KEY",
+   apiUrl: "https://api.zapfetch.com",
+ });
```

## Step 3 — Replace the API key

Swap your Firecrawl key for the ZapFetch key from Step 1. If you store it
in an environment variable, you're done — only the value changes.

```diff
- FIRECRAWL_API_KEY=firecrawl-key-here
+ FIRECRAWL_API_KEY=zapfetch-uuid-key-here
```

## Smoke test

Run one scrape to confirm the migration:

```bash
curl -X POST https://api.zapfetch.com/v1/scrape \
  -H "Authorization: Bearer $FIRECRAWL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com", "formats": ["markdown"] }'
```

Expected: HTTP 200 with a `data.markdown` field, and a credit-usage chunk
in the response envelope.

## Run both in parallel during cutover

Your Firecrawl Cloud key keeps working on `api.firecrawl.dev`, and your
ZapFetch key works on `api.zapfetch.com`. Migrate traffic gradually — for
example, route 10% of scrapes to ZapFetch, compare success rates and
markdown output for a day, then ramp up. There's no commitment to delete
the Firecrawl account; both keys stay live.

## FAQ

### Is ZapFetch a true drop-in for Firecrawl?

Yes for the Cloud API surface. Both `/v1/*` and `/v2/*` endpoints —
`scrape`, `crawl`, `search`, `map`, `extract` — are supported with
matching request and response schemas. Existing client code that reads
`creditsUsed` and `remainingCredits` from response envelopes works
unchanged. If you hit a behavioral difference, it is a bug — file it on
the Console.

### How does pricing compare?

ZapFetch is credit-based in USD. Failures are free, format multipliers
don't exist, and crawl is billed per **successfully fetched** page (not
per dispatched page). Current plans are outlined on
[Billing](/en/billing); the source of truth for your subscription is
`console.zapfetch.com/dashboard/billing`.

### What about rate limits?

See [Rate limits](/en/rate-limits). Defaults are generous on Free and
scale with paid plans. `429` responses include `Retry-After` so existing
SDK retry logic works without changes.

### Can I run both Firecrawl and ZapFetch simultaneously?

Yes — they're fully independent. Two keys, two base URLs, no
cross-account billing. Most teams cut over an endpoint at a time and
keep Firecrawl as a fallback for a billing cycle.

### Why is ZapFetch faster for APAC targets?

The API edge sits in Singapore, so traffic to `.jp`, `.kr`, `.cn`,
`.tw`, `.sg` domains traverses one regional hop instead of round-tripping
through US-east. The improvement compounds on crawls of e-commerce sites
that lazy-load over many requests.
